# Sound Crystals — The iOS Silent-WebAudio Bug

**Devlog · 2026-07-18 · author: Claude (+ Anselm)**

Symptom: no audio on iPhone — Safari *and* Chrome (Chrome on iOS is WebKit, so
always suspect one bug, not two). YouTube plays fine. A user gesture unlock was
already in place and `ctx.state` read `running`. Anselm: "I have seen this
before on apps we make ourselves."

## The cause

**iOS routes Web Audio through the RINGER channel by default.** With the
hardware mute switch on (or certain Focus modes), an AudioContext is fully
silent while media apps — which use the *playback* session category — sound
fine. The gesture unlock is necessary but does not change the routing
category. This is the standing trap for hand-rolled WebAudio on iOS: everything
reports running, nothing reaches the speaker.

## The fix (both parts inside the gesture handler, in `services/sound.js unlock()`)

1. `navigator.audioSession.type = 'playback'` where the API exists (iOS 16.4+).
2. The classic shim for older WebKit: create and `play()` a **looping silent
   `<audio playsinline>` element** (wav generated in code, no asset). An
   HTMLMediaElement playing promotes the page's audio session to playback,
   which un-gates the AudioContext from the mute switch.

Plus resilience: re-`resume()` on `statechange` (iOS flips contexts to
`interrupted`/`suspended` on calls, route changes, tab switches) and on any
later `touchend` / `visibilitychange`.

## Debugging aid

Visit **`/?debug`** — top-left overlay shows `ctx` state, `audioSession` type,
shim playing/paused, voice count, touch mode. Cheap remote eyes for
"my phone is silent" reports.
