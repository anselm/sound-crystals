# Sound Crystals — Mobile Mode

**Devlog · 2026-07-17 (later the same day) · author: Claude (+ Anselm)**

Anselm only has a phone to hand, so mobile came off the backlog immediately.
One new agent file, per the pattern: `agents/touch.js` + one manifest line.

## The mobile verbs

- **left thumb (bottom-left zone)** — virtual joystick, walk. Stick appears
  where the thumb lands rather than at a fixed spot.
- **drag anywhere else** — look (yaw/pitch on the camera, `YXZ` order, same
  convention as PointerLockControls so the two modes never fight).
- **tap** — ring the crystal under the finger (same toggle verb as the desktop
  reticle, aimed by touch; reach is doubled on phones since you can't aim as
  precisely). Body pass-through toggling still works untouched — it's just a
  distance test on the camera in `interaction.js`, however the camera moves.

## What it took beyond the new file

- `SC.touch` in config: `matchMedia('(pointer: coarse)')` — primary-pointer
  test so touchscreen laptops keep desktop mode.
- hud: conditional help text, and — the important one — **`bus.sound.unlock()`
  moved into the tap handler synchronously**. iOS will not resume an
  AudioContext from the async side of a bus dispatch; the gesture context is
  gone by then. Unlock first, then publish `{enter}`.
- interaction: skip `controls.lock()` on touch (no pointer lock on phones);
  touch.js publishes `{locked:true}` on enter instead so the hud hides.
- viewport meta (`maximum-scale=1, user-scalable=no`) + `touch-action:none` so
  look-drags don't scroll/zoom the page.

## Verified

`scripts/mobile.mjs`: emulates a 390×844 coarse-pointer phone over CDP and
drives real touch events through the actual pipeline — tap-to-enter (hud hides,
audio context running), joystick walk (camera z 5 → 2.28), look drag (yaw 0 →
0.6), tap-a-crystal (active flips, voice created, glow visible in screenshot).
Run against production after the autodeploy: same results at
https://crystals.exe.xyz.

Untested on real iOS hardware — the emulation is Chrome; Safari's audio-unlock
path is the standard risk. The synchronous-unlock pattern is the documented
correct one; if the field stays silent on a real iPhone, look there first.
